# 詳細クラス図生成ツール

詳細クラス図はシーケンス図と概念クラス図から機械的に導けるので、**仕様テキストは持たない**。
元の図を直したら作り直す、という運用にしている。
astah の API（`/usr/lib/astah_professional/astah-api.jar`）を Java から呼ぶのは 06 の `Gen.java` と同じ。

**入力は `../../06_シーケンス図/みるメモシーケンス図.asta`（2026-11-12 に `seq.spec` から切り替え）。**
図そのものが正なので、astah で図を直したらこのツールを回し直せば詳細クラス図が追従する。
逆に `seq.spec` を直しても、06 の `Gen.java` で `.asta` を作り直すまでは詳細クラス図に効かない。

## 2つの成果物

| ファイル | 作るツール | 中身 | 何に使うか |
| --- | --- | --- | --- |
| `../みるメモ詳細クラス図.asta` | `GenCls.java` | 4層（バウンダリ22／コントロール22／DM 1／エンティティ12）＋型2 | 提出物。**シーケンス図に書いてあることだけ**を写した版 |
| `../みるメモ詳細クラス図_エンティティ層補完版.asta` | `GenEnt.java` | エンティティ12＋DM | 検討用。シーケンス図に無かった操作も含めた版。ER図の下敷き |

2つに分けてあるのは、前者を**シーケンス図と1対1で照合できる状態に保つ**ため。
補完版を本体に混ぜると「どれがシーケンス図由来で、どれが後から足した分か」が追えなくなる。

## 使い方

```sh
ASTAH=/usr/lib/astah_professional
CP=".:$ASTAH/astah-api.jar:$ASTAH/astah-pro.jar"

javac -encoding UTF-8 -cp "$CP" GenCls.java GenEnt.java ClsDump.java

# シーケンス図に忠実な版（4層）
java -cp "$CP" GenCls \
  ../../06_シーケンス図/みるメモシーケンス図.asta \
  ../../03_概念クラス図/概念クラス図.asta \
  ../みるメモ詳細クラス図.asta

# エンティティ層補完版
java -cp "$CP" GenEnt \
  ../../03_概念クラス図/概念クラス図.asta \
  ../みるメモ詳細クラス図_エンティティ層補完版.asta
```

- `GenEnt` は概念クラス図の読み取りを `GenCls.readConcept()` に任せているので、2つまとめてコンパイルする。
- 入力・出力の .asta を astah で開いたままだと `ProjectLockedException` で失敗する。astah を閉じてから実行する。
- `ClsDump.java` は生成した .asta をクラス1つ1ブロックの表にして吐く確認用の道具（06 の `Dump.java` のクラス図版）。
  `java -cp "$CP" ClsDump ../みるメモ詳細クラス図.asta` で、作り直す前後の突き合わせに使う。
- 図を PNG にする: `sh $ASTAH/astah-command.sh -image all -f ../みるメモ詳細クラス図.asta -t png -o <出力先>`

## GenCls の変換規則

参考資料 `07詳細クラス図の書き方.pdf` に従う。

### クラス（p.2 機械的にオブジェクトを写す）

層は**ライフラインのベースクラスに付いたステレオタイプ**で判定する（06 の `Gen.java` が付けている）。

| シーケンス図のライフライン | 詳細クラス図 | 数 |
| --- | --- | --- |
| `<<boundary>>` | バウンダリ層のクラス | 22 |
| `<<control>>`（DM 以外） | コントロール層のクラス | 22 |
| `<<control>>` の `DM` | DM 層のクラス | 1 |
| `<<entity>>` | エンティティ層のクラス | 12 |
| `<<actor>>` | **書かない**（アクターはシステムの外） | - |

ステレオタイプが付いていないライフラインがあると、どの層に置くか機械的に決まらないので
**黙って流さず例外で止める**（図名とライフライン名を出す）。手で図を直したときに取りこぼさないため。

層のパッケージとは別に「型」パッケージを作り、属性の型（`String` / `Date`）をそこに置く。
理由は下の「判断したところ」9 を参照。

### メソッド（p.3 メソッドを機械的に移す）

**受信したメッセージを、受信側クラスのメソッドにする。** 送信側ではない。

- 可視性は `+`、戻り値は `void`（`+ ログインする() : void`）
- 同じクラスが同じ名前のメッセージを複数の図で受けても1つにまとめる（出現順）
- 宛先がアクターのメッセージ（`〜画面の表示`）は書かない
- 返信メッセージ（破線）は受信側のメソッドにしない
- 生成メッセージの判定は**メッセージ名ではなく astah の `<<create>>` そのもの**を見る（名前を変えても追従する）。
  扱いは下の「判断したところ」を参照

### 多重度（p.5）

| 関連 | 多重度 |
| --- | --- |
| 画面 — コントロール | 1 — 1 |
| コントロール — DM | 1 — 1 |
| DM — エンティティ | 1 — 1 |
| エンティティ — エンティティ | 概念クラス図から写す（コンポジションも含む） |

## GenEnt の変換規則

入力は概念クラス図だけ。シーケンス図は見ない。

- **エンティティの判定**：関連を1本以上持つか、属性を1つ以上持つクラス。
  概念クラス図に型として置かれている `String` / `Date` は外す（結果12クラス）
- **操作**：全エンティティに CRUD の4つを機械的に与える
  - エンティティ … `<エンティティ名>情報の<取得|登録|更新|削除>要求()`（12×4＝48）
  - DM … `<エンティティ名>情報を<取得|登録|更新|削除>する()`（同じく48）
- **属性・エンティティ間の関連と多重度**：概念クラス図から写す（GenCls と同じ）
- DM — エンティティは 1 — 1

## 判断したところ（機械的変換では決まらなかった分）

1. **`Createメッセージ` を DM → エンティティで受けた場合**、`<エンティティ名>情報の登録要求()` というメソッドにした。
   そのまま落とすとエンティティ層から登録系が消えて、CRUD の C だけ無い層になるため。
   名前は seq.spec 内の `管理履歴情報の登録要求` に合わせた。
2. **`Createメッセージ` をコントロール → 画面で受けた場合は書かない。** これは画面遷移であって、
   クラス図には出さない（PDF p.7 の例にも画面間の線は無い）。結果として**画面遷移はこの図から読めない**。
   読めるようにするなら画面遷移図を別に見る。
3. **エンティティの属性は概念クラス図にある分だけ写す。** 作品・感想・お気に入り・閲覧履歴・管理履歴・
   視聴媒体は属性が空のまま出る（＝概念クラス図の時点で未定）。ここで埋めると ER 図・テーブルレイアウトでの
   判断を先に消費してしまうので、空を空のまま見えるようにしてある。**補完版でも埋めていない。**
4. **クラス名・メソッド名は日本語のまま。** PDF p.6 はローマ字／英語への置き換えを求めているが、
   他の成果物が全部日本語なので合わせた。置き換えるならこの図を直すのではなく、`GenCls.java` に
   対応表を足して生成し直すのが筋。
5. **DM のメソッドはシーケンス図のぶんを全部書いた（29個）。** PDF p.7 の例は `データの作成/取得/更新` に
   丸めているが、丸めるとどのコントロールがどの DM メソッドを呼ぶかがクラス図から読めなくなる。
6. **補完版の DM メソッド名は `<エンティティ名>情報を<CRUD>する` で統一した。**
   seq.spec では `ユーザ情報を取得する` と `評価を登録する` のように「情報」の有無が揺れている。
   補完版は機械生成なので揃えた。**つまり補完版と本体で DM のメソッド名がずれている。**
   どちらかに寄せるなら seq.spec 側を直して GenCls を回し直す。

7. **入力を `seq.spec`（テキスト）から `みるメモシーケンス図.asta`（図そのもの）に替えた。**（2026-11-12）
   切り替えても出てくる図の中身は変わらない（切り替え前後で `ClsDump` の出力が完全一致：
   クラス59・メソッド・属性・関連74本すべて同じ）。変わるのは**どちらを直したら追従するか**だけ。
   - **却下した選択肢：`シーケンス図（仮）.puml`（16図・ユースケース単位）を元にする。**
     却下理由（ユーザーの判断）——「puml の方は UC 単位で書いていたから、本来のシーケンス図の書き方と
     ずれてくる」。この演習の作法は画面単位（参考資料 `06シーケンス図の書き方.pdf` ／スキマパークの作例）なので、
     UC 単位の仮版を元にすると層の名前も単位も作法から外れる。仮版とそれを元にした `シーケンス図（仮）.asta` は破棄。

8. **図とメソッドの並び順は、astah プロジェクトの要素順とライフラインの左→右の順で読む。**
   図名のソート順（`Dump.java` がやっている方）にすると会員側と管理者側が混ざるため採らなかった。
   結果として `seq.spec` で書いた順（会員側 → 管理者側）がそのまま残る。

9. **属性の型（`String` / `Date`）は「型」パッケージに逃がす。**
   astah は属性に組み込みでない型名を与えると、**属性の持ち主と同じパッケージに同名の未定義クラスを自動で作る**。
   そのままだとエンティティ層に `String` と `Date` が並び、層が12ではなく14クラスになっていた。
   - 実測：`int` / `float` / `boolean` は所有者を持たない組み込みの型として解決される（パッケージに現れない）。
     `String` / `Date` / `LocalDate` はクラスとして作られる。「String が特別」ではなく「組み込みの一覧に無い名前」が作られる
   - 同じことが `概念クラス図.asta` でも起きている（手で描いた図にも `String` / `Date` がクラスとして居る）。
     astah の動きであって生成ツールの都合ではない
   - 対処：本体の属性を作る前に「型」パッケージの中で型名を1回ずつ使い、型クラスをそちらに作らせてから消す。
     以後の属性はその型クラスに解決されるので、エンティティ層は12クラスちょうどになる
   - 属性の型表示（`ユーザ名 : String`）は残る。図の上の箱は1つも動かない（確認済み：57箱・関連74本が差分なし）

10. **図ではレイヤを縦位置だけで表す。区切り線もレイヤ名も入れない。**
    参考資料は同じ資料の中で描き方が食い違っている。
    - p.4「レイヤ分けする」… 赤い区切り線3本とレイヤ名（バウンダリレイヤ等）を描いている
    - p.7「詳細クラス図例（日本語）」… 区切り線もレイヤ名も無く、縦位置だけで層を表している

    作例である p.7 に合わせた。レイヤ分けはモデル側のパッケージ（バウンダリ／コントロール／DM／エンティティ／型）で
    担保していて、図はそれを縦位置で見せる。**astah の API では区切り線（`createLine`）・レイヤ名（`createText`）・
    パッケージの枠（`createNodePresentation` の親指定）はどれも描けるが、入れないことを選んだ。**
    パッケージの枠で囲む案は、バウンダリだけで22クラス入る枠が図を支配するうえ、枠のタブにレイヤ名が必ず出るため採らなかった。
